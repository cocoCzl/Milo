# 内存与 macOS 拼音输入诊断（2026-11-16）

## 结论与范围

本轮保留现有大纲和普通 UI，不实现 EditorView 驱逐，不修改输入事件、保存、恢复或退出协调逻辑。未确认真实内存泄漏，也未解决候选期间快捷键字符混入。新增设施只在显式诊断构建中统计资源和补充输入事件字段，普通构建不安装诊断插件、NodeView 包装器或输入监听器。

初始源码为 `0ba03b0`，诊断源码提交为 `bad7c34`，直接在 master 测量和修改，没有创建分支/worktree，没有推送或发布。主机为 arm64、macOS 27.2.1（26B131），Tauri Release、1280×820、Light、界面/文档缩放 100%。使用独立应用标识 `io.github.milo.validation20261116`，未使用用户原会话或真实文档。此验收不代表 Universal 发布验收。

## 正常 Release 基线

先使用未修改代码构建正常 Release，再运行已有 `create-native-profile-fixtures.mjs` 和 `sample-native-memory.mjs`。20 篇样本是同一个 `small-mixed` 合成文档；各场景默认在恢复/访问操作结束后等待 30 秒采样。Home 的两次采样没有统一计时锚点，表中取后一次。1、5、10、20 标签场景分别启动独立进程；20 标签后的三轮在同一个进程中完成。

单位为十进制 MB（1 MB = 1,000,000 bytes），不是 RSS。总数采用 `footprint` 的聚合 total footprint，不能直接相加各进程列或重复计算共享 IOSurface。采样脚本精确匹配临时应用路径，并要求相对于启动前进程清单只有一个 WebContent、GPU、Networking；身份不明确时停止。

首轮编辑通过原生界面完成并逐文件检查磁盘：19 篇插入同一合成文本；第 20 篇逐键输入时发生拼音候选混入，确认并保存后为一个合成列表项。第二、三轮重新打开的就是这些已保存文件，没有每轮再编辑；通过样本目录侧栏逐篇打开并访问，采样前隐藏侧栏。因此三轮有共同文档身份、内容和进程，但首轮与后两轮操作路径不同，不是严格同负载的线性泄漏检验。

三次关闭后的总数不是单调增长；WebContent 在第三轮关闭后还低于第一轮。但只有三轮短文档、没有对象可达性/完整 heap 证据，结论是“未确认真实泄漏”，不能声称排除泄漏。WebContent 的保留容量和 GPU 波动明显；仅看文件数、RSS 或单次进程总数不能归因于 EditorView。这里的 135.48 MB 也不能替代历史不同窗口/样本下约 200 MB 的恢复结果。

## 优化前后与最终普通构建

没有实施内存优化，所以不存在可宣称的优化后收益。不能把诊断构建与普通构建、不同样本或不同等待时机拼成收益百分比。补丁过程中正常 arm64 Release 的额外采样用于检查诊断开关关闭时的行为与波动，仍不是缓存优化效果；当时使用第一版计数补丁（之后只补强诊断构建中重配置去重），不是带事件追踪的诊断构建。

| 项目 | 修改前 | 修改后 |
| --- | --- | --- |
| 后台已访问 EditorView 策略 | 标签关闭前保留 | 相同 |
| 未访问标签 | 不挂载编辑器 | 相同 |
| 撤销历史、dirty、保存/恢复 | 既有语义 | 相同 |
| 有界缓存/驱逐 | 未实现 | 未实现 |
| 可证明的 footprint 收益 | 无 | 无；不报告优化百分比 |

额外正常构建在相同已保存样本的首次全部访问后为 253.23 MB。关闭后同锚点 30.5/120.0 秒分别为 153.57/154.06 MB，但首次采样因工具调度实际晚了 27.5 秒，不能称作“立即”。下一轮首次采样延迟 11.8 秒，为 181.03 MB；30/120 秒为 181.92/182.23 MB。这些波动进一步说明没有稳定的优化对照收益。

为获得即时样本，最后一次额外复核在打开文档前预启动只读采样器，轮询独立测试应用的 settings，等非空 startupSession 变为空后采样；不操作 UI，也不读取正文。以“空会话落盘被观察到”的时刻为锚点，检测间隔 20 ms，启动首次采样只差 2 ms。这个锚点包含设置持久化延迟，不等同最后一次点击的精确时刻；比事后启动命令更能反映释放开始时的状态。

## 资源与历史生命周期

新增计数仅在诊断构建中包装 EditorView 实例及 NodeView 的实际 `destroy` 方法，区别于 React 清理时先移除资源探针。用 WeakSet 识别 view 实例，插件重配置不会被误算成新建/销毁视图；对应测试包含真实 EditorView 的 reconfigure。计数器只保存数字，弱集合不阻止回收；诊断包装器不注册外部强引用。它证明 destroy 方法执行，不等于证明底层 JS 对象已经 GC 或 WebKit/GPU 缓存已归还操作系统。

| 原生诊断快照 | EditorView 创建 | 销毁 | 存活 | 文件监测目录 / 订阅 |
| --- | ---: | ---: | ---: | --- |
| 恢复 20 篇，仅首篇访问 | 1 | 0 | 1 | 1 / 20 |
| 20 篇全部访问 | 20 | 0 | 20 | 1 / 20 |
| 全部关闭 | 20 | 20 | 0 | 0 / 0 |

最终实例 destroy 包装实现又在原生诊断 Release 中重跑了该完整序列，仍为 1/0/1 → 20/0/20 → 20/20/0，探针列表为空；没有用旧版插件生命周期计数代替最终实现验收。

另一个混合样本会话创建 6 个视图；关闭包含本地/远程图片、代码块、表格的文档后，图片 NodeView 从创建 2/销毁 0/存活 2 变为创建 2/销毁 2/存活 0；对应代码块和表格各销毁 1 个，其他打开文档仍各保留 1 个。最后一轮恢复/撤销检查创建 4 个视图，关闭后 4 个全部销毁，所有 DOM 编辑器、Source textarea、文件监测订阅为 0。

- 图片：本地 NodeView 清空 `onload/onerror/src`，使异步回调失效；远程图片默认未加载，销毁时移除其点击监听。没有为本轮测试主动发起远程图片请求。已加载远程大图的解码缓存释放量没有被本样本测量。
- 监听器：既有浏览器资源测试中，20 个已访问视图的 document `selectionchange` 为 21，关闭后回到 Home 的 1；编辑器 `pointermove`、`resize`、`milo:find` 等计数归零。Playwright 自身增加的捕获监听器另行识别，不能当作应用泄漏。节点内部监听器、WebKit 内部监听器没有逐对象 heap 证明。
- 订阅：原生 20 个打开标签共享 1 个父目录监测器，全部关闭后目录和订阅为 0。上下文订阅只在活跃编辑视图观察到 2 个，后台为 0；关闭后探针列表为空。React 清理负责 unsubscribe，插件 destroy 清空上下文快照。
- 历史：后台视图保留 EditorState 与完整 ProseMirror history。本轮见到普通段落 undoDepth 4、标题 2，切换标签后实际撤销成功；没有通过清空历史降低内存。关闭移除探针和上下文中的 state/view 强引用，但未通过 heap/GC 确认每个历史对象回收。

`tests/probes/viewLifecycle.test.ts` 证明 EditorState/history 能在原始 ProseMirror view 重建后撤销/重做，但 Milkdown 内部插件闭包仍拥有原始 view；仅设置公共 `editorViewCtx` 不能安全转移销毁所有权。一个正确的驱逐方案还须明确状态所有权、图片/监听器清理、dirty 正文、源码模式、滚动、大纲和恢复身份的重建协议。当前证据不足以安全合入“当前 + 少量最近视图”缓存。

## 原生拼音复现矩阵

使用 macOS 自带简体拼音（`com.apple.inputmethod.SCIM.ITABC`），逐个调用原生按键输入 `n/i/...`，没有用粘贴、JS 赋值或合成 composition 代替输入法。输入源读取、可信 composition 事件和空格确认后的中文共同确认走过真实输入法；截图只看到了标记串，没有可靠捕获系统候选浮窗。按键仍由自动化工具投递，不是人工实体键盘验收。

| 位置 / 动作 | 实际观察 | 磁盘 / 结论 |
| --- | --- | --- |
| 普通段落，候选中 Cmd+S | 标记串增加 s；`meta=true` 的 KeyS 到达，保存进入 wait-stable | 确认后中文包含快捷键影响，手动保存及重开一致；未修复 |
| 标题，候选中 Cmd+S / Cmd+Q | 均影响候选，s/q 键带 meta 与 composing 到达 | 确认后保存了受影响的中文；Q 未产生原生 quit 请求 |
| 代码块，同上 | 与标题相同的组合事件及候选影响 | 围栏代码内中文落盘；未修复 |
| 表格单元格，同上 | 受影响文字留在单元格，未串到普通段落 | 单元格 Markdown 实际落盘；未修复 |
| Source，同上 | 原生 textarea 同样产生候选影响；Source 组合状态正常结束 | 完整 Source 文本落盘；未修复 |
| 普通段落，候选中 Cmd+Q | 标记串增加 q，DOM 收到 meta=true KeyQ | 未触发原生 quit，不能作为退出快捷键通过证据 |
| 确认后立即 Cmd+S | compositionend → settled → 非 composing KeyS → save/flush | 磁盘包含正确确认的中文，通过该样本 |
| 确认后立即切换标签 | 组合结束，切换成功 | 自动保存保留正确中文，重新打开一致 |
| 确认后关闭窗口 | 收到 native:close-request(window)；文档已保存 | 隐藏的瞬间被自动化重新激活影响，未独立确认整个视觉过渡 |
| 确认后退出应用 | 原生 Quit 菜单能进入协调；未保存样本出现保存并关闭提示，确认后进程退出 | 磁盘/重开一致；末次输入源已变 ABC，不能把它算作“中文确认后立即退出”完整通过 |
| 最小化、切换应用后继续输入 | 尝试原生最小化按钮；打开独立对照应用后再返回 Milo | 未可靠确认最小化瞬间；切换后输入源发生变化，中文连续输入这一格仍未验收 |

关键事件顺序：在普通段落的候选 Cmd+S 样本中，`compositionupdate`、`beforeinput(insertCompositionText)`、`input(insertCompositionText)` 出现在命令 `keydown(KeyS, meta=true, isComposing=true)` 前约 27 ms。随后 `session:save` / `session:wait-stable(composing=true, flushed=false)` 到达；空格确认产生 deleteCompositionText、insertFromComposition、compositionend，再 settled。保存没有在候选仍活动时把预编辑串当最终内容强行写盘。

因此，Milo 的 keydown 保存入口执行前，标记串已经被改变；仅阻止 keydown 或屏蔽 s/q 既太晚也会损害正常拼音。Source 与 ProseMirror 都出现现象，排除了“只发生在 Milkdown 标题/表格插件”的假设，但不能排除共享应用处理、输入法、WKWebView 或自动化投递。

临时最小 Cocoa/WKWebView 对照（只有 contenteditable 和 textarea、无 React/Milkdown/保存处理）只获得 ABC 输入，未产生 composition；Ctrl+Space 未可靠切换输入源，系统输入菜单也未能通过自动化访问。该对照不具可比性，不能据此声称是上游缺陷。没有人工实体键盘或正确拼音对照证据，根因仍未确认，不提交 IME 修复。

诊断事件新增 `commandCode`（仅带修饰键的 KeyS/KeyQ）和捕获阶段 `defaultPrevented`。后者不是应用处理完成后的状态。CompositionEvent 没有 `isComposing` 属性，现改记 null，避免把“无此字段”误报为 false。继续不记录正文、composition data、路径或普通可打印键；缓冲上限仍为 2048。
