# Known Issues

Milo is under active development and testing. This document tracks known product issues and post-redesign work without treating them as resolved.

## Preferences invisible modal — historical P1; confirmed animation mechanism removed

**Current status (2026-10-23):** No known reproducible invisible, input-blocking preferences modal remains in the tested final Release package. The confirmed transparent-entry mechanism has been removed, not merely made less likely. This does not establish that every historical paint failure is resolved. Retain the historical P1 impact for traceability; an unknown page-visibility cause alone is not a release blocker. For this issue, the evidence supports a staged **Pre-release**, rather than an unconditional stable-release sign-off.

**Historical failure and comparison.** Version 0.2.1 at `7253c80` was checked on an arm64 Mac running macOS 27.0.1 (26A434). In the bundled Debug application, cold launch into an isolated empty session followed by opening settings from the sidebar produced an active modal without visible dialog or backdrop. It was observed again after rebuilding with read-only diagnostics. This is a repeated local reproduction under native automation, not a proven deterministic recipe for ordinary foreground use or other machines. Native screenshots showed missing pixels, with modal focus/input isolation active; exposing the window restored drawing.

Diagnostics recorded nonzero layout bounds, close-button focus, `document.visibilityState === 'hidden'`, both entry animations running at time zero for over a minute, and opacity `0` on both surfaces. This confirms a direct mechanism: the modal becomes interactive while its visible appearance depends on a stalled animation clock. It does not establish why the page was hidden. Background/minimized pages may legitimately be hidden; focus and window capture alone do not prove that an unobscured foreground window incorrectly reported hidden. Portal placement, positioning and backdrop filtering have not been established as causes.

**Permanent treatment and evidence.** Remove the two preferences entry animations and keyframes; retain immediate appearance, existing layout, Radix modality and dependencies. The comparison was a rebuilt and restarted Debug application, not live removal of animation in the failing instance. Its diagnostic record at `2026-10-22T15:32:20.613Z` still reported hidden, but both surfaces had opacity `1`, no entry animation, and a centered dialog; native tool capture showed visible surfaces during that comparison. The capture was viewed in the tool session, but a standalone comparison PNG was not retained. The retained JSONL supplies the hidden/style evidence, not independent pixel proof. Temporary diagnostics were removed before packaging. The unchanged original Release application was normal on its first opening only: it was not reproduced there, and that limited check does not exclude Release susceptibility.

CSS review confirms the default visible appearance no longer waits for animation execution or completion. Dark/warm themes change surface tokens without hiding the modal; reduced-motion explicitly keeps animation disabled. The nested select has no transparent entry animation. CSS regression tests assert the positive no-animation/default-visibility contract and centering, rather than only the absence of old keyframe text. Application tests exercise backdrop dismissal, reopening and Escape, checking restoration of body pointer events and portal removal; existing tests cover trigger focus. These are useful regression guards, not proof of native painting or a full CSS cascade simulation.

**Final Release acceptance.** The universal DMG was built with `scripts/build-macos-universal.sh`, mounted read-only, and its executable checked against the build. On this arm64 host, 30 actual open/close cycles were completed and visually reviewed: 10 without a document, 5 with unsaved content, 5 in dark appearance at interface/document zoom 120%/110%, and 10 in warm appearance with English labels. Close button, Escape and backdrop dismissal were rotated. Additional native checks covered select interaction, focus/input isolation, sidebar and Focus Mode changes, native window zoom/restore, Finder switching, minimize/restore, continued editing and saving, and preference/document persistence after restarting. No missing modal pixels or residual input lock appeared within that scope. The final diagnostic-free Release was not instrumented to establish simultaneous hidden state; that evidence belongs to the modified Debug comparison above.

Previously completed checks: 362 frontend tests, 33 Rust tests, TypeScript, ESLint, Prettier, rustfmt, Clippy and macOS builds passed. The bounded follow-up reuses that acceptance and package; it changes documentation only. `tauri dev` session restoration previously blocked on a directory read, so the Debug observations concern bundled assets, not the Vite frontend. Real settings/session data were restored after the original acceptance and were not changed for this follow-up. Intel and older supported macOS versions have not been exercised on hardware.

**Bounded visibility-impact review.** Application source contains no direct `visibilitychange`, `document.hidden` or `visibilityState` branching. Preferences operations/persistence do not await animation frames. Ordinary Auto Save uses a one-second timer, which the runtime may throttle in the background. There are animation-frame schedulers for block/selection toolbar positioning and active-heading UI, and one safety-critical dependency: composition completion waits for consecutive stable rendering frames before allowing saves. If those frames remain suspended, an IME composition can keep automatic/manual saving deferred until settlement. Existing tests cover composition notification/settlement, blocking writes and save-and-close while composing, and saving confirmed content after settlement; the follow-up passed 14 targeted tests across the editor IME and document-session suites (35 unrelated cases excluded by the test filter). They do not demonstrate native IME recovery under persistent hidden/frame suspension. No such save failure or data loss was reproduced in this preferences investigation. Do not bypass this safety boundary or falsify page visibility. Actual foreground IME recovery is a remaining targeted validation item, not evidence that the old invisible modal still exists.

**Release boundary.** Recommend a staged Pre-release for this preferences change with the above limitations disclosed. Remaining user-facing risks are an unobserved alternative paint failure on untested environments and possible delayed UI/IME-save settlement if rendering frames remain suspended. Before stable sign-off, sample normal foreground Chinese IME input into a disposable saved document, switch away/minimize and return, then confirm Auto Save/manual save and reopen the saved text; include Intel/older macOS coverage where available. A confirmed persistent foreground save block or invisible modal in the final package would require reassessment. Unknown hidden-state provenance alone does not require continued root-cause research. Distribution/signing requirements in `RELEASE.md` are separate from this issue assessment; this unsigned local artifact has not passed that public-distribution gate.

Prior acceptance artifact (before the local fix commit): `src-tauri/target/universal-apple-darwin/release/bundle/dmg/Milo_0.2.1_universal.dmg`, version 0.2.1, based on `7253c8078892f2381b9fc4c37933d77509a629f6` plus the uncommitted preferences CSS change (accompanied by test/documentation changes). **Technical closeout (2026-10-23).** A real IME check was attempted in the existing Release application using a new disposable document and native key input. Input-source shortcut attempts followed by individual `n`/`i` keys produced literal Latin text, without an observed Chinese candidate window. Consequently none of the requested candidate-confirmation/save timing scenarios is claimed as passed. No synthetic composition events or pasted Chinese text were substituted for real IME acceptance. The disposable document was closed without saving; existing documents and settings were not reset. A human check remains: in a disposable saved Markdown file, confirm a distinct Chinese phrase, then separately test idle Auto Save, immediate app switching, minimize/restore, immediate manual save, and close/normal exit with save protection. Reopen and compare actual disk text after each case; unconfirmed/cancelled candidates are not expected saved text. Keep this verification gap separate from an observed save failure.

## P2 — WebKit soft-wrap boundary caret painting

At some soft-wrap boundaries, WebKit can paint the native caret in an unexpected visual position. ProseMirror selection, DOM state, Markdown, and dirty state remain correct. This is currently treated as a visual issue.
